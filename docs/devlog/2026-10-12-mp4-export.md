# 브라우저에서 30초 1080p MP4 내보내기

## 목표와 제약

4주차 완료 기준은 "30초 분량 프로젝트를 1080p mp4로 내보낼 수 있다"였다. 서버 없이 브라우저에서
디코딩(WebCodecs) → 합성(Canvas) → 인코딩(WebCodecs) → MP4 먹싱까지 해야 한다. 소리는 넣지 않기로 했다.

## 설계

1. **프리뷰와 같은 합성**: 프레임 i의 시각 `frameToUs(i, fps)`에서 `resolveLayers(project, time)`로 레이어를 구하고,
   프리뷰와 함께 쓰는 `drawLayers`로 1920×1080 `OffscreenCanvas`에 그린다. 텍스트도 같은 `drawTextOverlay`를 쓴다.
2. **건너뛰지 않는 디코더**: 프리뷰 재생은 늦으면 프레임을 건너뛰지만(시계가 우선), 내보내기는 한 프레임도 빠지면 안 된다.
   클립마다 `ClipFrameReader`를 두고 필요한 프레임이 나올 때까지 `await`한다. 지난 프레임은 즉시 `close()`하고,
   클립이 끝나면 리더를 해제한다(같은 영상을 나눈 클립은 서로 다른 위치를 읽으므로 클립별 리더).
3. **인코딩·먹싱은 mediabunny**: `CanvasSource.add()`가 인코더가 밀릴 때 기다려 주므로 프레임이 메모리에 쌓이지 않는다.
4. **코덱 대체**: H.264 → VP9 → AV1 중 실제 인코딩 가능한 첫 코덱을 고른다. 이 테스트 환경(Linux headless Chromium)은
   H.264 인코더가 없어 VP9이 쓰였고, H.264가 아니면 재생 호환성 안내를 띄운다.
5. **시작 시점의 Project 고정 + 모달**: 불변 Project를 그대로 넘기므로 내보내는 중 편집이 결과에 섞이지 않는다.
   모달 뒤 편집기에는 `inert`를 걸어 클릭·포커스·보조기기 접근과 단축키를 막았다.

## 결과 (Chromium headless)

영상 10개(3초씩) + 위 트랙 이미지 + 30초 텍스트로 만든 30초 프로젝트:

| 항목             | 값                         |
| ---------------- | -------------------------- |
| 형식             | MP4 / VP9                  |
| 해상도·fps       | 1920×1080, 30fps           |
| 프레임 수 / 길이 | 900 / 30.000초             |
| 크기             | 8.0MB                      |
| 걸린 시간        | 약 24~25초 (실시간과 비슷) |

`ffmpeg`로 1.5초 프레임을 뽑아 보니 원본 테스트 영상에 찍힌 타임코드도 1.5초(45프레임)로 정확했다.

## 겪은 일

- 진행률 표시의 남은 시간을 렌더 중 `performance.now()`로 계산했다가 React 린트(purity)에 걸렸다.
  경과 시간은 진행률 콜백에서 계산해 상태에 넣고, 렌더는 상태만 읽도록 바꿨다.
- 다운로드 파일 이름이 `download`로 나왔다. 최소 재현으로 확인해 보니 headless Chromium이 **영문이 아닌 파일 이름**(`30초 테스트.mp4`)만
  `download`로 바꾸는 테스트 환경 특성이었다(영문 이름은 그대로). 그 과정에서 링크를 문서에 붙여 클릭하고 object URL을 10초 뒤 해제하도록 다듬었다.

## 배운 점

- 실시간 재생과 오프라인 렌더링은 같은 합성 함수를 쓰되 "시간을 어떻게 진행시키는가"만 다르다:
  재생은 시계를 따라가며 늦은 프레임을 버리고, 내보내기는 프레임이 준비될 때까지 시간을 멈춘다.
- 이상한 결과가 나오면 앱 코드를 고치기 전에 최소 재현으로 환경 문제인지 먼저 가른다.
