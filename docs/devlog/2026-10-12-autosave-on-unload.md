# 새로고침 직전 편집이 사라지는 자동 저장 고치기

## 문제 상황

편집할 때마다 Project를 500ms 디바운스로 IndexedDB에 저장하고, 탭을 숨기거나 닫을 때(`pagehide`, `visibilitychange`)는
대기 중인 저장을 즉시 실행하도록 만들었다. 단위 테스트(메모리 저장소 + 가짜 타이머)는 모두 통과했다.

그런데 실제 Chromium에서 "글자 크기를 바꾸고 바로 새로고침"하면 **마지막 편집이 사라지고 그 전 값이 복원**되었다.

| 시나리오                | 편집 값 | 새로고침 후  |
| ----------------------- | ------- | ------------ |
| 편집 직후 바로 새로고침 | 100     | 72 (이전 값) |

## 원인

`pagehide`에서 저장을 "시작"은 하지만, IndexedDB는 비동기 API라서 트랜잭션이 끝나기 전에 문서가 내려가면 중단된다.
`await db()` → `transaction()` → `put()` → `tx.done`으로 이어지는 마이크로태스크·요청 사이에 페이지가 사라진다.
단위 테스트는 저장소를 메모리 구현으로 바꿔 끼워서 이 문제를 볼 수 없었다. **실제 저장소로 브라우저에서 새로고침해 봐야만 드러나는 버그**였다.

## 해결: 동기 비상 백업

- 페이지를 떠날 때 아직 저장되지 않은 변경이 있으면(`autosave.hasPendingChanges()`), Project JSON을 `localStorage`에 **동기적으로** 쓴다.
  Project는 미디어를 담지 않는 순수 데이터라 수십 KB 수준이다(원본 파일은 가져올 때 이미 IndexedDB에 저장됨).
- 시작할 때 IndexedDB 저장본과 백업을 모두 검증(`parsePersistedRecord`)하고 `savedAt`이 더 최근인 것을 복원한다(`pickLatestRecord`).
  백업이 이기면 IndexedDB에 다시 저장하고 백업을 지운다. 깨진 백업은 무시한다.

결과: 편집 직후 새로고침을 5번 반복해도 5번 모두 마지막 편집이 복원되었다.

## 함께 한 것

- **저장본은 믿지 않는다**: IndexedDB의 값은 이전 버전이거나 손상되었을 수 있어 `unknown`으로 받고 런타임 타입 가드로 검사한다.
  참조 무결성(클립이 가리키는 트랙·에셋 존재)까지 확인하고, 실패하면 빈 프로젝트로 시작하되 저장본은 지우지 않는다.
  실제로 IndexedDB에 깨진 값을 넣고 새로고침해 이 경로를 확인했다.
- **복원은 편집이 아니다**: `projectStore.loadProject`로 Project를 교체하고 히스토리를 비운다. 이전 세션의 커맨드로 복원된 Project를 되돌리면 안 된다.
- **복원이 끝나기 전에는 편집기를 그리지 않는다**: 복원 전 편집이 자동 저장으로 저장본을 덮어쓰는 경쟁을 원천적으로 막는다.

## 배운 점

- 테스트 대역(메모리 저장소)은 로직을 검증하지만, "페이지가 사라지는 순간" 같은 실행 환경의 성질은 검증하지 못한다.
  저장·복원처럼 브라우저 생명주기에 걸친 기능은 실제 브라우저에서 새로고침까지 해 봐야 한다.
- 언로드 시점에는 동기 API만 믿을 수 있다. 무거운 저장은 평소에 비동기로, 마지막 순간은 작고 동기적인 백업으로 나눈다.
